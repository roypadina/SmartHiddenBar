# SmartHiddenBar

macOS 27 menu bar app: hides every status item left of its own icon via MenuBarAgent's private allow-list (left click = per-display click mode `clickModes[screen.localizedName]`: cycle show → icon bar → hide / toggle / icon bar only; ⌥-click / hotkey open the icon bar with everything currently off the bar, under our icon; no double click — the icon is drawn by MenuBarAgent, so a click on it first hits our global monitor: `barUp` treats a bar closed < 0.5 s ago as open). `alwaysHidden` bundles stay restricted even while shown (restriction then active in both states); `newApps = hide` adds never-seen bundles (`knownApps`) to it. Optional hover / click on bare menu bar (`hoverReveal`, `clickEmptyBar`; AX hit test role AXMenuBar at x and x ± 20 pt, since icon gaps up to 16 pt also report AXMenuBar). Assessment mode blocks Notification Center even with `com.apple.notificationcenterui` allowed (tested), so a clock click (`com.apple.menuextra.clock`) lifts the restriction until NC has no on-screen window. Hiding applies from the cached inventory first (`hideNow`), the AX walk runs in parallel (~130 processes × ~20 ms), lists every app's item via the Accessibility API (`AXExtrasMenuBar`) and mirrors their menus (right-click → Menu Bar Apps ▸; menu = Show Items/Hide Items · Disable/Enable · Menu Bar Apps ▸ · Settings… · About · Support · Quit SmartHiddenBar; `disabled` = no restriction at all, always-hidden included, any click opens the menu, persisted), optional icon bar (⌥-click / its shortcut). Five global shortcuts recorded in Settings (`Shortcuts.swift` `shortcutActions`, Carbon hot keys): show/hide items, icon bar (default ⌃⌥B; the old `hotkey` preset migrates once), list apps, settings, quit — all others default off. Stored as `toggleShortcut` / `barShortcut` / `appsShortcut` / `settingsShortcut` / `quitShortcut` = `"keyCode:carbonMods"`, `""` = off. ⌃⌥M clashes with Wispr Flow. Settings/About/Welcome open through `AccessoryWindows` (Settings.swift: regular app + Dock tile while a window is open, `.accessory` after) with a minimal main menu; opening the app again shows Settings (`applicationShouldHandleReopen`); the Welcome window (Welcome.swift, `didShowWelcome`, re-entry Settings → About → Welcome Guide…) replaces the first-run alert; the status icon turns into a warning triangle without Accessibility or after a failed hide. Swift sources in the repo root (`*.swift`), built by `./build.sh` (icon set chosen by `SET=` at its top, assets in `Assets/icons/`, regenerated by `Assets/icons/gen.py`).

## Rules
- **Always run the `/Applications/SmartHiddenBar.app` copy, never `build/`.** On macOS 27, MenuBarAgent resolves allow-listed bundle ids through LaunchServices, which picks the `/Applications` copy; a copy running from `build/` never matches, so the allow-list hides its own icon wherever it sits. `build.sh` installs to `/Applications` unless that copy is running — quit it first, then rebuild.
- Launching/relaunching SmartHiddenBar from a session is OK (Roy, 2026-10-02) — `open /Applications/SmartHiddenBar.app` (it inherits the session env even with `env -u`; harmless — the app spawns no children); quit with `osascript -e 'quit app "SmartHiddenBar"'`. Never drive his UI otherwise (no pressing, clicking or key events).
- Signing: `build.sh` uses a stable local code-signing identity (the name set in `build.sh`; ad-hoc fallback) so the Accessibility grant survives rebuilds. Ad-hoc signing changes the cdhash every build and re-prompts. Reset a broken grant with `tccutil reset Accessibility com.roypadina.SmartHiddenBar` (Screen Recording: `tccutil reset ScreenCapture com.roypadina.SmartHiddenBar`).
- Log: `~/Library/Logs/SmartHiddenBar.log`. Defaults domain `com.roypadina.SmartHiddenBar`.
- Git: public repo `roypadina/SmartHiddenBar`, pushed over SSH. Commit with the repo-level GitHub noreply address (GitHub email privacy rejects a private address). Commit + push after each working fix.
- `probe/` (gitignored) holds two trivial status-item apps for isolating menu bar issues. To test allow-list behaviour, copy a probe to `/Applications` with a fresh bundle id: MenuBarAgent matches allow-listed bundle ids only for apps running inside `/Applications` (a helper nested in an `/Applications` app works; `~/Library/Application Support` never does, even as the only registered copy; allowing the parent app's id does not help a nested helper — probe matrix 2026-10-30) and only when LaunchServices resolves the id to that copy, so a probe run from `probe/build` is never "allowed" (this misled the 1.1.3 release-once fix). `menuBarCanShow` (AX.swift) encodes the rule and `applyHide` logs violators. Prove visibility by AX hit-test at the item's frame (must return the probe's pid) or a screenshot (`screencapture -x -R0,0,<width>,30`: the session terminal has Screen Recording but no Accessibility); AX frames stay on-bar for restriction-hidden items. A standalone allow-list harness (MenuBarClientCore activate → screenshot → invalidate) tests the rule without SmartHiddenBar running. New probes always appear leftmost (`NSStatusItem Preferred Position` is ignored on macOS 27), so placing one right of our icon needs Roy's ⌘-drag. Apps with System Settings → Menu Bar → "Allow in the Menu Bar" off are parked by macOS at creation, whatever our list says.
- Left/right is decided only on a settled read (`settledRead`, AX.swift): our own frame is sampled from 0.5 s before the AX walk to its end; any move = retry (3×, 0.3 s), then keep the list. Other apps' AX frames trail a re-layout (iStat Menus, Slack), so a read during or right after items appear/vanish/resize mislabels neighbours (issue #7 follow-up, 1.4.1). Stress test: a probe whose title flips width on a flag file, placed right of a second probe right of our icon.
- Self-check (pure logic, no app): `swiftc -target arm64-apple-macos27.0 AX.swift tests/main.swift -o build/selfcheck && build/selfcheck`. Not in CI (the runner can't run a macOS 27 binary).
- In zsh, `log` is a builtin: use `/usr/bin/log stream ...`.
